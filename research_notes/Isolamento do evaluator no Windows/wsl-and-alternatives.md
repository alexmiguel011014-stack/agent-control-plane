# Alternativas gratuitas de isolamento para G2.2 em Windows 10 Pro

## WSL2 pode ser endurecido o suficiente neste Windows 10?

### Takeaway
WSL2 tem a melhor experiência de terminal e oferece controles úteis de montagem e interoperabilidade, mas a documentação atual marca networkingMode=none como disponível somente no Windows 11 e requer Windows 11 22H2. No Windows 10, WSL2 com Bubblewrap ou NsJail pode ser investigado como uma camada Linux adicional, mas não satisfaz G2.2 até as quatro propriedades serem demonstradas; a falha local observada (Wsl/E_ACCESSDENIED) também impede usá-lo agora.

### Cited Findings
- WSL2 executa um kernel Linux em uma VM utilitária leve, mas distribuições são contêineres isolados dentro da mesma VM e compartilham kernel, namespace de rede, árvore de dispositivos, CPU, memória e swap. [Microsoft: WSL architecture](https://learn.microsoft.com/en-us/windows/wsl/about)
- .wslconfig configura globalmente as distribuições WSL2. Em wsl.conf, automount enabled=false desliga automount de drives, mas a documentação diz que eles ainda podem ser montados manualmente ou por fstab; mountFsTab=false impede o processamento automático desse arquivo. interop enabled=false bloqueia lançamento de processos Windows pela distribuição e appendWindowsPath=false deixa de inserir caminhos Windows no PATH. [Microsoft: WSL configuration](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)
- A tabela atual lista networkingMode=none como rede desconectada, mas as notas de rodapé limitam as opções de rede à disponibilidade no Windows 11 e ao Windows 11 22H2 ou posterior. A mesma página diz que .wslconfig global requer Windows Build 19041+; isso não remove a restrição específica da opção de rede. [Microsoft: WSL configuration, notas da tabela](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)
- As configurações wsl.conf são por distribuição; interoperabilidade está disponível desde Windows 10 1809. Uma conta Linux padrão pode ser configurada em builds compatíveis; o comando do host também pode escolher usuário explicitamente com a opção --user. [Microsoft: WSL configuration](https://learn.microsoft.com/en-us/windows/wsl/wsl-config); [Microsoft: WSL basic commands](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)
- O FAQ da Microsoft ressalta que WSL dá acesso automático a arquivos Windows, adiciona caminhos Windows por padrão e pode executar binários Windows. Também descreve o usuário WSL como tendo controle completo de suas instâncias Linux. [Microsoft: WSL FAQ](https://learn.microsoft.com/en-us/windows/wsl/faq)
- O terminal do host pode iniciar uma distribuição; wsl --terminate encerra a distribuição escolhida e wsl --shutdown encerra todas as distribuições em execução. A documentação não afirma que --terminate é um contrato de encerramento de árvore de processos com evidência de ausência de órfãos após um prazo. [Microsoft: WSL basic commands](https://learn.microsoft.com/en-us/windows/wsl/basic-commands); [Microsoft: WSL configuration](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)
- Bubblewrap é um utilitário Linux sem privilégio para montar um namespace de filesystem restrito; suporta mounts somente leitura, PID namespace e network namespace, que contém apenas loopback. O próprio projeto diz que a proteção depende integralmente dos argumentos e que tudo que for montado pode introduzir riscos. [Projeto Bubblewrap: README](https://github.com/containers/bubblewrap/blob/main/README.md)
- NsJail é descrito pelo projeto como isolamento de processos Linux com namespaces, limites de recurso, cgroups e filtros seccomp-BPF; inclui namespaces de montagem, PID, rede e usuário. O README descreve build por fonte e dependências de desenvolvimento Linux. [Projeto Google NsJail](https://github.com/google/nsjail)

### Inferences
- Em um WSL2 funcional, uma configuração candidata é: usar WSL2; armazenar uma cópia descartável do repositório apenas dentro do filesystem Linux; desligar automount e processamento de fstab; desligar interop e inserção de PATH; executar como usuário Linux não-root sem sudo disponível ao código; montar dentro do Bubblewrap só o toolchain e os arquivos de tarefa permitidos, com fonte somente leitura e uma pasta scratch gravável. Isso reduz canais de acesso comuns, mas automount desligado não proíbe mount manual e a distribuição ainda compartilha o kernel da VM WSL.
- Como networkingMode=none não está oficialmente disponível no Windows 10, uma network namespace do Bubblewrap poderia negar rede ao processo Linux mesmo com a rede do WSL conectada. Isso é hipótese para teste, não garantia para a máquina: provar que processos no namespace não chegam a DNS, IPv4/IPv6, interface do host, gateway, localhost nem serviços do Windows.
- Para confidencialidade do oracle, não deixar o código depender de um workspace Windows montado: importar somente a cópia autorizada da tarefa e deixar evaluator/oracle fora do VHD da distro. Interop e automount desligados reduzem exposição acidental, mas não transformam WSL numa VM sem integrações nem impedem montagem manual por si sós.
- A terminação da distribuição inteira é candidata para cortar processos descendentes, porém G2.2 pede evidência observável de encerramento de toda a árvore no prazo. O comando sozinho não fornece essa evidência.

### Gaps
- Confirmar build exato do Windows, versão WSL/distro, política local que causa Wsl/E_ACCESSDENIED, suporte a user namespaces/cgroups no kernel WSL e se o usuário consegue iniciar WSL sem elevação. Nada disso foi testado nesta pesquisa.
- Provar, com sondas benignas e sem usar patches gerados, filesystem deny, ausência de rede, encerramento de processos e inacessibilidade do oracle. Testar também que configurações malformadas ou não suportadas não são silenciosamente ignoradas.
- O comportamento de wsl --terminate com árvore de processos/fork e a possibilidade de um processo alcançar integrações do host precisam de teste local. Não iniciar benchmark de código gerado antes do gate G2 manual aprovado.

## Hyper-V ou Windows Sandbox são caminhos viáveis no Windows 10 Pro?

### Takeaway
Hyper-V oferece a separação mais explícita e configurável; Windows Sandbox pode dar uma VM descartável com menos manutenção se o recurso ausente for habilitado. Ambos são incluídos no Windows Pro, mas exigem configuração de recursos do host com privilégios administrativos; a usabilidade de terminal e a automação precisam ser validadas. Para um evaluator, a VM dedicada sem adaptador virtual e sem compartilhamentos é o candidato de maior isolamento; o Sandbox é o candidato de menor custo operacional.

### Cited Findings
- Hyper-V é um recurso opcional incluído no Windows 10 Pro/Enterprise, sem download separado; requisitos documentados incluem SLAT, extensões de virtualização, virtualização habilitada no BIOS/UEFI e ao menos 4 GB de RAM. A habilitação por PowerShell exige sessão elevada (administrador). [Microsoft: Install Hyper-V](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/get-started/install-hyper-v)
- Switch Hyper-V privado permite comunicação apenas entre VMs no mesmo host, sem rede ao host ou ao exterior; contudo, outra VM ligada ao mesmo switch ainda participa dessa rede privada. Um switch interno conecta o guest ao host. [Microsoft: Hyper-V network planning](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/plan/plan-hyper-v-networking-in-windows-server)
- PowerShell Direct funciona entre host e guest Windows 10 com Hyper-V independentemente da configuração de rede. Pode fornecer prompt interativo, executar comando/script e copiar arquivos, mas requer que o operador seja administrador Hyper-V, que o guest tenha perfil e credenciais válidos e que o host execute uma sessão administrativa. [Microsoft: PowerShell Direct](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/powershell-direct)
- Hyper-V Stop-VM -TurnOff desliga a VM como se a energia fosse cortada e pode perder dados não salvos. Como o guest inteiro para, é candidato para encerrar processos e descendentes no timeout; a ausência de processos órfãos deve ser confirmada após a parada. [Microsoft: Stop-VM](https://learn.microsoft.com/en-us/powershell/module/hyper-v/stop-vm)
- Integrações Hyper-V incluem serviço de cópia de arquivos host↔guest e PowerShell Direct sem rede. Serviços podem ser habilitados/desabilitados por VM; Enhanced Session pode redirecionar clipboard/drives, então não se deve presumir que esses canais estejam ausentes sem conferir configuração. [Microsoft: Hyper-V Integration Services](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/integration-services); [Microsoft: Use local resources on Hyper-V](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/use-local-resources-virtual-machine-connection)
- Windows Sandbox faz parte das edições compatíveis como Pro, usa o hypervisor para executar um kernel separado e descarta software, arquivos e estado ao fechar. Windows 10 1903+ e virtualização habilitada são requisitos; Microsoft documenta pelo menos 4 GB RAM, 1 GB livre e dois núcleos. Habilitá-lo requer recurso opcional e PowerShell administrativo, com reinício se solicitado. [Microsoft: Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/); [Microsoft: Install Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-install)
- Windows Sandbox inicia com rede e clipboard habilitados por padrão. Um arquivo .wsb permite desabilitar rede, clipboard, vGPU, mapear diretório do host somente leitura e disparar um LogonCommand. O usuário do container é administrador no Sandbox; aplicativos instalados no host não estão disponíveis dentro dele e dependências precisam ser instaladas ou fornecidas dentro de cada instância descartável. [Microsoft: configure Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file); [Microsoft: Windows Sandbox overview](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/)
- A observação recebida para a máquina diz que o binário do Windows Sandbox não está presente. Portanto, o Sandbox não é utilizável no estado constatado; documentação indica que pode ser um recurso opcional a habilitar, mas isso não foi verificado localmente.
- Windows 10 Home/Pro chegou ao fim de suporte em 14 de outubro de 2025; extensões ESU ou edições LTSC têm ciclo próprio. O estado de ESU desta máquina não foi confirmado. [Microsoft Lifecycle: Windows 10 Home and Pro](https://learn.microsoft.com/en-us/lifecycle/products/windows-10-home-and-pro); [Microsoft: Windows 10 end of support](https://learn.microsoft.com/en-us/windows/release-health/release-information)

### Inferences
- Hyper-V é o caminho preferido se o administrador puder habilitá-lo: VM exclusiva, sem vNIC (ou switch privado dedicado verificado), sem compartilhamento de pastas/clipboard, sem passe de discos do host, disco de entrada com apenas a tarefa descartável e disco de saída separado. Para guest Windows 10, PowerShell Direct oferece fluxo controlável pelo terminal, mas o serviço do evaluator deve expor somente operações fixas; não passar uma sessão administrativa do host ao modelo.
- Um guest Linux Hyper-V pode evitar licença adicional de Windows, mas PowerShell Direct documentado exige guest Windows 10+. Interação terminal e transferência de saída com rede desligada precisam de um canal aprovado (por exemplo, console/artefato em disco), com desenho e teste próprios. Não presumir que uma console VMConnect seja automatizável como CLI.
- Windows Sandbox pode executar via .wsb + LogonCommand e produzir resultados numa pasta scratch exclusiva mapeada com escrita. Isso mantém o fluxo iniciável por arquivo/terminal, mas ainda pode abrir janela GUI; automação de timeout/fechamento e captura de resultado são lacunas até teste. Mapear output gravável deixa essa pasta exposta ao código e não deve incluir oracle, arquivos pessoais ou diretórios pais.
- Uma pasta de fonte mapeada somente leitura para Sandbox protege a cópia do host contra gravação, mas o código ainda pode ler seu conteúdo; não mapear fonte/oracle secreto junto. O Sandbox executa como administrador dentro do guest, então sua adequação depende do kernel virtualizado e dos canais de integração cuidadosamente desligados.

### Gaps
- Verificar de forma read-only se a máquina satisfaz requisitos Hyper-V, se o recurso/serviços já estão ativos, se a virtualização está habilitada, se existem permissões administrativas disponíveis e se o Windows 10 está em ESU/LTSC. Habilitação/reboot não foi tentado.
- No Hyper-V, confirmar a rede desligada no nível da VM e testar sem DNS, IPv4, IPv6, gateway, host ou egress; provar que nenhuma pasta, oracle ou disco físico é visível ao guest. Validar que o processo de timeout força TurnOff e que após isso nenhum processo guest permanece.
- No Sandbox, se habilitado, confirmar a configuração efetiva de network/clipboard/vGPU, testar leitura/escrita fora dos dois diretórios mapeados, verificar isolamento do oracle e demonstrar fechamento automatizado dentro do prazo com processos-filhos ainda ativos.
- Verificar licenciamento e disponibilidade do toolchain no guest; no Sandbox a imagem é limpa a cada abertura e não herda programas instalados no host. A habilitação de um recurso Windows exige autoridade local e ficou fora do escopo desta pesquisa.

## O que acrescentam Bubblewrap, NsJail e Sandboxie Plus?

### Takeaway
Bubblewrap e NsJail são ferramentas Linux, não alternativas Windows nativas, que podem acrescentar namespaces, limites e filtros a WSL2 sem corrigir suas integrações com Windows nem oferecer outra fronteira de kernel do host. Sandboxie Plus funciona no Windows, mas sua documentação revela pontos incompatíveis com G2.2 sem endurecimento e prova: leitura de arquivos do host pode continuar disponível e o comando de terminar processos é somente uma solicitação sem confirmação de sucesso.

### Cited Findings
- Bubblewrap cria namespaces Linux: montagem permite escolher arquivos visíveis e montá-los somente leitura; PID namespace isola a visibilidade de processos e executa PID 1 para colher filhos órfãos; network namespace oferece apenas loopback. O README adverte que segurança depende dos argumentos e que sockets/arquivos montados podem abrir canais de risco. [Projeto Bubblewrap: README](https://github.com/containers/bubblewrap/blob/main/README.md)
- NsJail documenta execução única e limites de CPU, memória, descritores, número de processos, namespaces NET/PID/USER/MOUNT, cgroups e seccomp. Seu próprio README descreve ambiente de build Linux e dependências de compilação; não é um sandbox Windows nativo. [Projeto Google NsJail](https://github.com/google/nsjail)
- O repositório Sandboxie Plus declara Windows 7+ 64-bit, isolamento baseado em software de aplicações e driver/serviço gerenciável pelo programa. Core está sob GPLv3, enquanto SandMan UI tem licença customizada; o projeto permite uso não comercial, mas algumas funções precisam de certificado. Portanto, o conjunto Plus não é integralmente software livre sob uma licença única. [Sandboxie Plus: README](https://github.com/sandboxie-plus/Sandboxie/blob/master/README.md); [Sandboxie Plus: LICENSE.Plus](https://github.com/sandboxie-plus/Sandboxie/blob/master/LICENSE.Plus)
- A documentação de hierarquia diz que, se uma cópia não está no sandbox e a aplicação não tenta modificar o arquivo, a leitura pode ocorrer diretamente do arquivo original do host; ClosedFilePath é necessário para negar acesso a um recurso sensível. [Sandboxie Plus: file hierarchy](https://github.com/sandboxie-plus/sandboxie-docs/blob/main/docs/Content/SandboxHierarchy.md); [Sandboxie Plus: resource access](https://github.com/sandboxie-plus/sandboxie-docs/blob/main/docs/Content/ResourceAccessSettings.md)
- A documentação de rede descreve bloqueio via hooks Winsock em modo usuário como não cobrindo todas as APIs; WFP pode adicionar filtragem kernel, mas o projeto diz expressamente que não promete fail-closed em toda falha WFP. [Sandboxie Plus: Network Access](https://github.com/sandboxie-plus/sandboxie-docs/blob/main/docs/Content/NetworkAccess.md); [Sandboxie Plus: WFP Support](https://github.com/sandboxie-plus/sandboxie-docs/blob/main/docs/PlusContent/WFPSupport.md)
- Start.exe pode iniciar, parar e listar programas por linha de comando, mas não é um aplicativo console e seu output não aparece diretamente no prompt sem redirecionamento. /box:<name> /terminate pede ao serviço para terminar processos; a documentação atual diz que término imediato/sucesso não é garantido, é limitado à sessão do chamador, descarta o resultado do serviço e código de saída zero não confirma que todos os processos pararam. [Sandboxie Plus: Start command line](https://github.com/sandboxie-plus/sandboxie-docs/blob/main/docs/Content/StartCommandLine.md)

### Inferences
- Bubblewrap (menor complexidade) ou NsJail (mais controles de recursos/seccomp) podem ser camadas de controle de processo dentro de uma distro WSL2, desde que kernel e configuração permitam os namespaces/cgroups requeridos. Eles não devem ser apresentados como substitutos de Hyper-V/WSB; a fronteira externa ainda é WSL e networkingMode=none não está documentado para Windows 10.
- Sandboxie Plus poderia ser útil para aplicações comuns ou como camada complementar com ClosedFilePath explícito para oracle e WFP; não é o caminho mais simples para provar G2.2. A combinação de leitura por padrão, dependência do driver Windows e encerramento de processo sem confirmação o torna inferior a parar uma VM inteira para um benchmark de código potencialmente hostil.
- Instalação do driver Sandboxie exige instalação privilegiada do componente de kernel em uso real; validar UAC, assinatura e requisitos de reboot na build concreta. A documentação/repositório consultados não confirmaram o fluxo exato de instalação nesta máquina.

### Gaps
- Nenhum teste foi executado nesta pesquisa. São necessários probes determinísticos e benignos para negar leitura do oracle e escrita fora de scratch, negar DNS/TCP/UDP/IPv4/IPv6 e serviço local, e finalizar um processo que cria filhos/daemons. Repetir após timeout e confirmar ausência de órfãos.
- Para qualquer candidato escolhido, registrar hash/configuração da imagem, versão Windows/WSL/kernel/ferramenta, política de rede e mounts reais em execução; testar também falhas e configuração inválida para garantir fail-closed. Só após a evidência manual G2 pode o benchmark de patches gerados avançar.
