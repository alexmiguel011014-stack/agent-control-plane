# AppContainer launcher for the Windows evaluator

## 1. What each Windows primitive isolates (and does not)

### Takeaway

For a local, automatable Windows 10 evaluator, the most plausible process boundary is a zero-capability AppContainer (the documented lowbox launch path) plus an NTFS ACL on a private staging tree and a Job Object for process lifetime. AppContainer is not a mount namespace: its access is still governed by object ACLs and Windows deliberately exposes some system resources, so a literal claim that the process cannot read *any* file outside the workspace needs a VM boundary and a narrower definition of what is shared.

### Cited Findings

- Microsoft documents launching a desktop process as AppContainer by creating/deriving a per-app Package SID, placing it in `SECURITY_CAPABILITIES`, adding `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` to `STARTUPINFOEX`, and calling `CreateProcess` with `EXTENDED_STARTUPINFO_PRESENT`; this is supported starting with Windows 8. [Launch an AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer); [UpdateProcThreadAttribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute)
- An AppContainer token has a Package SID plus capability SIDs. Microsoft describes file/resource authorization as an intersection of the regular user/group permissions and Package/Capability permissions. It also states that regular AppContainers can access certain system files/directories and shared resources, while LPAC is stricter and requires explicit capabilities for resources available to regular AppContainers. [AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation); [Launch an AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer)
- Microsoft states that an AppContainer without network capability cannot access the network. Therefore do not grant `internetClient`, `internetClientServer`, or `privateNetworkClientServer`; treat any failed launch if a capability is unexpectedly required as fail-closed. [Launch an AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer); [Sockets and app capabilities](https://learn.microsoft.com/en-us/windows/apps/develop/networking/sockets)
- `CreateAppContainerProfile` creates a per-user/per-app profile and returns its SID. The published return codes include `E_ACCESSDENIED`; the API documentation does not list an administrator privilege as a prerequisite, but it does not promise profile creation will succeed under every account or policy. [CreateAppContainerProfile](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-createappcontainerprofile)
- DACLs are the access control mechanism for securable files/objects. Microsoft provides `SetNamedSecurityInfo`/`SetSecurityInfo` to set DACLs on NTFS files and directories, and inheritable ACEs can propagate to children. Grant the AppContainer SID access only to a fresh staging tree and the specific Node runtime/test files it needs; do not grant it access to the repository root or oracle directory. [How DACLs control access](https://learn.microsoft.com/en-us/windows/win32/secauthz/how-dacls-control-access-to-an-object); [SetSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setsecurityinfo); [ACE propagation](https://learn.microsoft.com/en-us/windows/win32/secauthz/automatic-propagation-of-inheritable-aces)
- A restricted token from `CreateRestrictedToken` can remove privileges, mark SIDs deny-only, and add restricting SIDs. Windows performs two access checks—one with enabled SIDs and one with restricting SIDs—and grants access only when both pass. That is useful privilege reduction, but it does not itself deny network access or create a filesystem namespace; DACLs still determine file access. [Restricted Tokens](https://learn.microsoft.com/en-us/windows/win32/secauthz/restricted-tokens)
- A Job Object groups processes for management and termination. By default, `CreateProcess` descendants join the job; a job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` terminates its members when the last job handle closes. Microsoft documents exceptions: `Win32_Process.Create` children are not automatically associated, and breakaway settings can exclude descendants. Job Objects provide no file or network boundary. [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

### Inferences

- The practical AppContainer profile should be unique per run, have no declared capabilities, and receive an explicit ACL only on a disposable workspace/runtime/test staging tree. Keep oracle files outside that tree and verify a denied read against the real oracle path; a normal same-user ACL check or a path allowlist alone is not evidence of isolation.
- Prefer LPAC if the supported Windows build and Node runtime work with it, because Microsoft documents fewer ambient resource grants. The docs do not establish that Node's runtime dependencies will work in LPAC, so regular AppContainer is the simpler initial compatibility target.
- Treat “filesystem containment” as a measured boundary (deny access to the repository/oracle/user-data sentinels while allowing only the staged workspace), not as proof that the process cannot read Windows system files. If the requirement literally means no host filesystem view at all, use a disposable VM and share only explicit input/output directories.

### Gaps

- Research did not run a no-admin profile-creation probe or verify the target machine's NTFS ACLs, AppContainer policy, Windows build, Node runtime access, or LPAC compatibility. `CreateAppContainerProfile` can return `E_ACCESSDENIED`.
- The Windows API docs establish the AppContainer/Job building blocks, not a finished audited Node launcher or a guarantee against Windows kernel vulnerabilities.

## 2. Can a Node/TypeScript parent launch it for free on Windows 10 Pro?

### Takeaway

`node:child_process.spawn` cannot create an AppContainer process by itself: its public options do not expose the Win32 `STARTUPINFOEX` security-capability/job attributes. A small native helper is the cleanest implementation; a fixed PowerShell 5.1 script using `Add-Type` plus C# P/Invoke is a no-new-package route to prototype the same APIs. Neither requires buying a sandbox product, and the documented AppContainer launch path does not call for elevation, but profile/ACL errors must stop execution. Windows Sandbox is stronger isolation, but Win10's documented automation is weaker than Win11 24H2's CLI.

### Cited Findings

- Node's `spawn()` options cover command, args, cwd, env, stdio, shell, and related process behavior; they do not expose `STARTUPINFOEX` or token/capability attributes. Node documents `subprocess.kill()` as sending a signal to the spawned child, and Windows emulates signals as termination of that target process. The Node docs do not claim descendant-tree termination. [Node.js child_process](https://nodejs.org/api/child_process.html); [Node.js process](https://nodejs.org/api/process.html)
- Windows' documented native launch API is `CreateProcess` plus `STARTUPINFOEX`; `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` selects AppContainer, and `PROC_THREAD_ATTRIBUTE_JOB_LIST` assigns the child to supplied jobs. Both attributes are documented for Windows 10; `JOB_LIST` is supported on Windows 10 and newer. `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` can constrain which inheritable handles are passed when `bInheritHandles=TRUE`. [UpdateProcThreadAttribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute)
- The Windows SDK provides headers/libraries and command-line compiler/linker tools; Microsoft documents Visual Studio Community as a free download. A C++ helper can use `CreateAppContainerProfile`/`DeriveAppContainerSidFromAppContainerName`, `InitializeProcThreadAttributeList`, `UpdateProcThreadAttribute`, `CreateProcessW`, `CreateJobObject`, and `SetInformationJobObject`. [Prepare your Win32 development environment](https://learn.microsoft.com/en-us/windows/win32/learnwin32/prepare-your-development-environment); [Launch an AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer)
- Windows PowerShell's `Add-Type` compiles supplied C# source and explicitly supports P/Invoke calls to unmanaged Windows functions. This allows a narrow P/Invoke launcher without installing a separate npm package or SDK; it still needs careful correct struct/handle marshalling and must be kept as trusted code. [Add-Type for Windows PowerShell 5.1](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.utility/add-type?view=powershell-5.1)
- Windows Sandbox is included with supported Pro editions and uses Hyper-V virtualization with a separate kernel. Windows 10 support starts at version 1903, but enabling the optional feature requires the Windows Features UI or an elevated PowerShell command and may require a restart; prerequisites include BIOS virtualization, 4 GB RAM minimum, 1 GB disk, and two CPU cores. [Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/); [Install Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-install)
- The documented `wsb` CLI begins with Windows 11 version 24H2. Its `exec` returns the exit code but has no process-I/O capture and requires an active user session; `stop` terminates the sandbox session. Thus Windows 10's supported `.wsb`/GUI flow can run a logon command and disable networking, but the documented Win10 interface is not an integrated, headless runner returning stdout/stderr. [Windows Sandbox CLI](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-cli); [Configure Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file)
- Sandboxie-Plus is an existing GPL-3.0 open-source Windows isolation project with command-line start/wait/terminate controls, process-tree controls, privacy mode, and per-sandbox WFP firewall features. It uses a driver and service; its project FAQ states administrative rights are required to start the service. It is a possible installed dependency but not a no-admin/no-install helper. [Sandboxie-Plus source](https://github.com/sandboxie-plus/Sandboxie); [Sandboxie-Plus command line](https://sandboxie-plus.com/sandboxie/startcommandline/); [Sandboxie-Plus FAQ](https://sandboxie-plus.com/sandboxie/frequentlyaskedquestions/)

### Inferences

- Recommended G2.2 launcher on Win10: a tiny trusted C++ helper, or a tightly scoped PowerShell/C# P/Invoke wrapper if the project forbids adding a compiler dependency. The Node caller should invoke only a fixed `public-test` operation, fixed `process.execPath`, fixed `--test`, normalized staged paths, a minimal environment, and fixed stdio; do not accept executable/shell text from task/model input.
- Build a Job Object with kill-on-last-handle-close and no breakaway flags. Add the job handle with `PROC_THREAD_ATTRIBUTE_JOB_LIST` at process creation, together with the AppContainer security-capabilities attribute. If the job cannot be applied or child creation fails, return `RUNNER_FAILURE` and never fall back to ordinary `spawn`. In the fallback design, create the child suspended, assign it to the job, then resume; terminate it if assignment fails. `PROC_THREAD_ATTRIBUTE_JOB_LIST` is preferable to the two-call fallback because it avoids a create-then-assign window.
- Use `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` to pass only stdout/stderr (and stdin if required); use a clean Unicode environment and AppContainer temp; place the Node executable and public-test sources in an explicitly readable staging tree. The model process must not see repository paths, original task files, `.env`, host profile data, the oracle, or arbitrary host executables through broad ACLs.
- A free native SDK/Community toolchain exists, but installing it would be a separate system/package change. The project rules prohibit package installation by the agent; first use an already-present compiler or evaluate the in-box PowerShell route. Sandboxie or Windows Sandbox feature enablement would also be an external system change, not part of this research task.

### Gaps

- The exact target Windows 10 edition/build, process outer-job constraints, SDK/PowerShell compiler availability, and policy restrictions are unknown. A standard-user process may successfully create a profile, but the API's `E_ACCESSDENIED` return prevents promising it without a host probe.
- Microsoft documentation does not provide a ready-made supported Node adapter; native helper code still needs independent review and post-gate behavioral probes. Windows Sandbox on Win10 has no documented `wsb` CLI, so full automation/timeout/stdio needs another mechanism.

## 3. Oracle confidentiality and the concrete G2.2 boundary

### Takeaway

The current oracle path is not isolated from candidate code: `oracle-runner.mjs` imports the hidden oracle, and that oracle imports candidate files into its own Node process. Moving only the oracle into a second same-user child does not protect it. Keep the oracle in a trusted parent process and run the candidate module in its own AppContainer worker; communicate through a deliberately narrow input/output protocol. If the oracle contract must stay as a direct same-process `verify(workspaceRoot)` import, it cannot meet the project's confidentiality gate.

### Cited Findings

- The project explicitly says snapshots do not create isolation and hidden tests stored under the same Windows user are not protection; G0.6 says no patch, public test, or oracle may run before G2.2. [GOALS.md](../../GOALS.md#L21); [GOALS.md](../../GOALS.md#L66)
- The evaluator's default `spawnProcess` is Node's regular `spawn`, with only cwd/env/stdio options, and timeout/output overflow calls `child.kill('SIGKILL')`. It then spawns `oracle-runner.mjs` from the host repository. [Evaluator](../../bench/evaluator/index.mjs#L192); [Evaluator](../../bench/evaluator/index.mjs#L209); [Evaluator](../../bench/evaluator/index.mjs#L387)
- `oracle-runner.mjs` dynamically imports the registered oracle from the repository and calls `verify(canonicalWorkspace)` inside the same runner process. [Oracle runner](../../bench/evaluator/oracle-runner.mjs#L48); [Oracle runner](../../bench/evaluator/oracle-runner.mjs#L51)
- The repo's evaluator README states the current harness is not a security sandbox and that a same-user process can reach task/oracle files without OS isolation. [Evaluator README](../../bench/evaluator/README.md#L7)
- The current attestation validator requires four checks to be boolean `true` and compares the baseline and runner hashes; this validates a JSON claim, not that each child was actually created with the claimed OS boundary. [Isolation attestation](../../bench/evaluator/isolation-attestation.mjs#L6); [Isolation attestation](../../bench/evaluator/isolation-attestation.mjs#L43)
- Microsoft documents that AppContainer isolates access to other applications' processes, files, registry, network, and credentials subject to the specific grants. Windows Sandbox gives a separate virtualized kernel and only mapped host folders are intentionally shared; clipboard and networking are enabled by default unless disabled in configuration. [AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation); [Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/); [Configure Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file)

### Inferences

- Required architecture change for `oracle_inaccessible`: host-side trusted oracle owns the hidden oracle data and expected comparisons; isolated Node worker loads only the candidate module and returns bounded outputs over inherited pipes or a private local channel. The oracle must not send its source, expected values, detailed assertion messages, stack traces, or sensitive protocol state into the worker. Rework each current oracle away from importing the candidate module directly.
- Stage a separate copy of the registered public test and the minimum Node runtime into the AppContainer's allowed tree; the workspace and public test can be read-only at execution time, while Node temp/cache output goes to the AppContainer profile. The original repository and `bench/oracles` remain outside its ACL grants.
- G2.2 evidence must come from running independent probes through the real production launcher: read/write host sentinels denied; workspace access allowed; network probes denied; a spawned grandchild is terminated on timeout/launcher close; oracle file and oracle host-process memory are inaccessible to the candidate. Store the evidence only after those checks pass; do not populate `checks: true` manually.

### Gaps

- The current oracle interface is direct module loading and cannot be made confidential merely by putting `oracle-runner.mjs` in another process. Changing to a request/response oracle requires redesigning task oracle interfaces and ensuring each task still tests useful behavior without disclosing hidden expectations.
- No OS-isolation probes, oracle protocol redesign, test run, patch execution, or oracle execution was performed for this research assignment. The existing G2.2 gate remains open.
